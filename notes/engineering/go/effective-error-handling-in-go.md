## Context

Error handling is one of Go's most debated features. This article from morsmachine.dk lays out practical patterns for handling errors idiomatically, focusing on readability and proper error type design.

**Source:** [Effective Error Handling in Go](https://morsmachine.dk/error-handling)

## Indented flow pattern

Check errors first with early returns. The "happy path" reads as a straight line down the page:

```go
if err != nil {
    // handle error
}
// continue with success logic
```

This is the foundational Go error-handling pattern. Guard clauses at function entry points keep the main logic unindented and readable.

## Define custom error types

Create package-specific error types so consumers can identify and distinguish errors by source. Implement the `error` interface through simple types or structured error types that expose context (like which file failed during parsing).

## Avoid over-wrapping errors

When wrapping errors from external packages, be cautious about losing critical type information. If your package uses an outside interface, do not wrap errors generated by calls to them. Users may need the original error type for proper handling via type assertions or type switches.

## Errors as state

Hold errors temporarily when appropriate:

- Until a buffer empties (like `bufio.Reader` accumulating errors)
- When the operation will likely repeat with identical parameters

This reduces repetitive error checking in hot paths without hiding failures.

## Extract repetitive error handling

When the same error-handling pattern appears multiple times, consolidate into helper functions:

- Dedicated error handler functions that encapsulate the check-and-respond logic
- Deferred helper functions that check for nil before executing cleanup

## Key takeaway

Structure error checks as guard clauses. Design public error types for package-specific exceptions. Preserve original error types from dependencies. Consolidate recurring error patterns into reusable functions. The goal is code where the successful execution path is immediately visible.
